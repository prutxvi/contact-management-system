# Contact Management System (Group 11)

A menu-driven C++17 console application for storing and managing personal contacts.

It meets every mandatory feature in the assignment brief, and it goes past the brief in one
specific way: each data structure is chosen for a measured reason, and every speed claim in the
demo is a number this repository produced on this machine (`make measure`).

```
src/contact_manager.cpp   the whole application, one submittable file
bench/bench.cpp           benchmarks that justify the data-structure choices
tests/test_cms.py         64 behaviour tests that drive the real binary
demo/                     a scripted demonstration and its saved transcript
docs/benchmarks.md        measured numbers (regenerated by `make measure`)
docs/viva_qa.md           viva questions with prepared answers
docs/explained.md        start here: the basics, the design, every workflow, how to edit safely
docs/report.md           the term project report: design, justification, algorithms, results
docs/idea_book.md         further ideas, ranked, with the DSA concept each one adds
```

## Submitting this as a term project

```sh
make package     # writes dist/Group11_ContactManagementSystem.zip
```

The archive contains the single submittable source file, the report, a saved sample run, and a
build/run note. Nothing in it needs a network connection, a package manager or an IDE.

## Build and run

```sh
make            # builds ./cms
make run        # runs it against ./contacts.csv
make test       # builds, then runs the 64 behaviour tests
make measure    # rebuilds docs/benchmarks.md from this machine
make demo       # replays demo/steps/in.txt and writes demo/session.log
```

Manual build, no make needed:

```sh
c++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -o cms src/contact_manager.cpp
./cms --data contacts.csv         # --seed adds sample data when the file is empty
./cms --data contacts.csv --audit # run the index self-check and exit
./cms --data contacts.csv --inject-fault 3 --audit   # corrupt an index on purpose, then audit
```

`--audit` exits 0 when every index agrees with the record array and 1 when it does not, so it can
be used as a check in a script. `--inject-fault 1..5` is a testing hook: it breaks one index after
loading so that the audit can be shown to detect damage rather than merely to report success.

The program compiles clean with `-Wall -Wextra -Wpedantic`. It uses no third-party libraries and
no platform-specific calls (no `system("cls")`, no `conio.h`).

## Why these data structures

Six structures hold one record collection, each doing one job:

| Structure | Job | Why not something simpler |
|---|---|---|
| `std::vector<Contact>` | storage of record | dense and contiguous, so printing and sorting walk memory linearly; a `std::list` would scatter every record across the heap for no benefit, because we pick the delete strategy around it |
| `std::unordered_map<int, size_t>` | ID -> slot | an ID lookup must not cost a scan; this makes update and delete start in O(1) |
| `std::unordered_map<std::string, size_t>` | phone -> slot | exact phone lookup and the duplicate check are both O(1) average; a sorted array would cost O(log n) and a scan O(n) |
| `std::map<std::string, std::vector<size_t>, CiLess>` | lower-cased name -> slots | gives ordered traversal and a prefix range for free, and the value is a *list* because two people may share a name |
| `Trie` | name prefix -> IDs | autocomplete in O(prefix length + matches) instead of scanning every name, and the DFS returns matches in alphabetical order without an extra sort. Honest caveat: against the ordered map at a few thousand records the trie is about 2x *slower* (see `docs/benchmarks.md`); it wins by 5-7x against a linear scan, and it wins outright for long keys or letter-by-letter suggestion as the user types |
| `std::deque<Action>` | undo history | bounded to the last 20 changes; `std::stack` cannot drop the oldest entry, `std::deque` can |

### Cost of every operation

`n` = contacts, `k` = matches returned, `p` = prefix length, `L` = name length, `q` = query length.

| Operation | Cost | Note |
|---|---|---|
| Add contact | O(1) amortised + O(log n) + O(L) | vector append, name-index insert, trie insert |
| Find by ID | O(1) average | hash map |
| Find by phone, exact | O(1) average | hash map |
| Find by phone, partial | O(n * L) | linear scan; a partial match cannot use a hash |
| Find by name, exact | O(log n + k) | ordered map |
| Find by name, prefix | O(log n + k) | one `lower_bound` then walk while the prefix matches |
| Find by name, substring | O(n * L) | no index can help with an arbitrary substring |
| Find by name, typo-tolerant | O(n * L^2) | Damerau-Levenshtein per record |
| Autocomplete | O(p + k) | trie walk plus subtree walk |
| Update contact | O(1) + O(L) | locate by ID, repair the two affected index entries |
| Delete contact | O(1) + O(L) | swap-with-last, then repair only the moved record |
| Display, sorted | O(n log n) | `std::stable_sort` over `n` pointers |
| Validate indexes | O(n * (L + log n)) | audit walks every record and every index entry |
| Save / load | O(n) | one pass, plus index rebuild on load |
| Undo | O(1) + O(L) | one recorded action |

### The delete strategy, in one paragraph

The obvious delete is `vector::erase`, which is O(n) because every later record moves. Instead the
last record is moved into the hole and the array is popped. That is O(1) of movement, but it
invalidates every index entry that pointed at the old last slot. Exactly one record moved, so
exactly one record needs re-indexing: unlink it from its old slot, relink it at the new one. The
measured result is in `docs/benchmarks.md` (about 46x faster than `vector::erase` on 100,000
records). Display order is not lost, because IDs are monotonic and every display sorts by ID,
name, phone, group or date anyway.

### Why phone numbers are strings

`9876543210` does not fit in a 32-bit `int`; it overflows to `2147483647` silently. Numbers that
start with `0` would lose the leading zero. Storing the phone as a `std::string` avoids both
problems and lets the record hold a normalised, displayable value at the same time.

## Beyond the brief

1. **Phone normalisation.** `+91 90000 11111`, `090000-11111` and `9000011111` all become
   `9000011111`, so a duplicate cannot hide behind formatting.
2. **Three search modes plus fuzzy.** Exact, prefix, substring, and typo-tolerant
   (Damerau-Levenshtein, so `Ananaya` still finds `Ananya`).
3. **Trie autocomplete.** A separate menu option, because a trie is a syllabus structure worth
   showing on its own.
4. **Undo.** The last 20 changes are reversible, including a delete.
5. **CSV persistence that survives real data.** A proper quoting routine and a character-level
   parser handle commas, double quotes and embedded newlines. A save writes to a temporary file
   and renames, so a failed write cannot destroy the previous file.
6. **Header-driven loading.** Columns are matched by name, so a reordered or extended CSV still
   loads. Bad rows and duplicate phones are skipped and counted in the load message.
7. **Measured evidence.** `bench/bench.cpp` times the hash map against a sorted array and a linear
   scan, the trie against a linear scan, swap-delete against `vector::erase`, and
   `std::sort` against `std::stable_sort`, and counts the comparisons each one performs.
8. **Idea detection.** The statistics report flags records that share a name and near-duplicate
   names at edit distance 1 or 2, which is how a typo turns into two contacts.
9. **Index audit with a test hook.** Menu option 14 walks every record and checks that all four
   indexes agree with it, and `--audit` runs the same check headlessly. To prove the check is not
   vacuous, `--inject-fault 1..5` deliberately corrupts one index and the audit is asserted to
   catch each of the five cases in `tests/test_cms.py`.
10. **Real tests.** 64 behaviour tests drive the compiled binary through stdin and check its
   output, including the index repair after a swap-delete, the audit's sensitivity to injected
   damage, and a byte-stable CSV round trip.

## Edge cases that are covered on purpose

| Case | Behaviour |
|---|---|
| Menu choice is not a number, or out of range | rejected, menu repeats |
| Phone contains letters only, or no digits | `Invalid phone 'abc': no digits found.` |
| Phone is short, or 11+ digits, or starts with 0 or 1 | rejected with the rule that failed |
| Phone already in use, in a different notation | rejected, and the message names the owner |
| Name is empty, or spaces only | rejected |
| Name is all digits | rejected |
| Name has runs of spaces, or padding | collapsed to single spaces and trimmed |
| Name is repeated across two contacts | allowed, and the statistics report lists it |
| Email is malformed | rejected |
| Update would take another contact's phone | rejected, self excluded from the check |
| Update a record that does not exist | `No contact with ID n.` |
| Delete a record that does not exist | `No contact with ID n.` |
| Delete with the confirmation declined | nothing changes |
| Undo a delete whose phone was re-added | refused with the reason |
| Search with an empty query | refused instead of matching everything |
| Search on an empty list | says the list is empty, distinct from "no match" |
| Display or sort an empty list | specific message, no crash |
| CSV has a wrong header | rejected with the required columns named |
| CSV has duplicate phone rows | first kept, the rest counted and skipped |
| Save target directory does not exist | error reported, in-memory data untouched |
| Write fails part way through | previous file left intact, error reported |
| Input stream ends mid-prompt | program exits cleanly instead of looping |

### Deterministic order without relying on stability

`std::stable_sort` keeps records that share a name in ID order, which is what the demonstration
uses. The other fix, and the one a production system would prefer, is to make the comparator a
total order by breaking ties on the ID: `(lower(name), id)`. Then even `std::sort` is
deterministic. The sorting experiment runs all three and shows 0 reordered tie-pairs for both
fixes, against 95 for plain `std::sort`.

## Display limits, stated honestly

- Column widths assume single-width characters. Very long names and addresses are ellipsized in
  the table and shown in full by the update screen.
- The near-duplicate name scan is pairwise and O(n^2), so it is skipped above 200 records and says so.
- The fuzzy search scores every record, so it is the slow path by design; `docs/benchmarks.md`
  gives its measured cost.
- Records are held in memory. The CSV file is the whole persistence layer.
